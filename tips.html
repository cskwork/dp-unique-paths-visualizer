Solving Mindset

How to think before you code

Before you reach for a specific algorithm, a few habits shape how you approach any problem: read the constraints, find the structure, and prove the move before you make it. Pair these with the problem library and the pattern field guide.

Ten mindset tips

Durable habits that work across every problem on this site, from the first easy grid walk to the hardest DP recurrence.

01

Read the constraints before the algorithm

The same problem statement with n <= 20, n <= 10^5, or n <= 10^9 points at three different solution families. Read the bounds before you pick an approach.

02

Restate the problem in your own words

Convert the story text into five things:

  • input
  • output
  • operation
  • objective
  • constraints
03

Start with brute force first

Always ask: "What is the simplest correct solution?" Get the right answer on paper, then optimize only the bottleneck.

04

Identify the real bottleneck

Is the problem hard because of time, memory, repeated computation, ordering, search space, or state explosion? Naming the cost tells you what to fix.

05

Look for structure, not tricks

Tricks expire; structure repeats. Common structures to name first:

  • sorted order
  • prefix / suffix
  • graph edges
  • overlapping subproblems
  • monotonicity
  • frequency counting
  • intervals
06

Ask: what must I remember?

This question often reveals the data structure for free:

  • hash map, heap, stack, queue, set
  • tree, union-find
  • DP table
07

Reduce the problem to a known pattern

Match the shape of the question to a pattern:

  • "choose best among previous values"→DP / greedy
  • "shortest steps"→BFS
  • "dependencies"→topological sort
  • "continuous subarray"→sliding window / prefix sum
  • "can we achieve X?"→binary search on answer
08

Prove why it works before coding

Especially for greedy. Ask: "Why is this local choice safe?" If you cannot explain it, it may be wrong.

09

Design edge cases before implementation

Walk the idea through these inputs in your head:

  • empty input
  • one element
  • duplicates
  • all same values
  • negative numbers
  • maximum size
  • the impossible case
10

Code for invariants, not just steps

Know what each variable always means, at every line. For example:

  • left is the first valid index
  • dp[i] means best answer ending at i
  • heap holds current candidates only

The one question that matters most.

Don't start with "Which algorithm should I use?"

Start with "What prevents the brute-force solution from being fast enough, and what repeated work or structure can I exploit?"

Algorithms are answers. That question is how you earn the right to them, one problem at a time.
